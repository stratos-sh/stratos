The reconcileNodePool function has cyclomatic complexity 46 -- it handles scale-up, monitoring, scale-down, max-runtime recycling, standby replenishment, and status updates in a single ~230-line function. This is the largest refactoring task in Phase 5.

Extract each logical phase into a private helper method on the Reconciler receiver:

1. **`handleScaleUp(ctx, nodePool, nodes) error`** -- Extract the scale-up decision logic (check demand, start standby nodes, launch new if needed)
2. **`handleMonitoring(ctx, nodePool, nodes) error`** -- Extract warmup monitoring and cloud warmup monitoring
3. **`handleScaleDown(ctx, nodePool, nodes) error`** -- Extract scale-down logic (identify excess running nodes, drain, stop)
4. **`handleMaxRuntimeRecycling(ctx, nodePool, nodes) error`** -- Extract max-runtime check and recycling
5. **`handleStandbyReplenishment(ctx, nodePool, nodes) error`** -- Extract standby pool maintenance
6. **`updateNodePoolStatus(ctx, nodePool, nodes) error`** -- Extract status update logic

The refactored reconcileNodePool should be a simple orchestrator that calls each helper in sequence and handles errors. Each helper should be a focused function with complexity well under 15.

**Critical:** This is a behavior-preserving refactoring. Each helper must preserve the exact same logic, error handling, and return behavior as the original code block. Do not change any business logic, just extract into methods.

Place helpers in the same file (reconciler.go) since they are private methods of the Reconciler and part of the reconciliation flow. If the file gets too long (over 300 lines after extraction), move the helpers to a new `reconciler_helpers.go` in the same package.
